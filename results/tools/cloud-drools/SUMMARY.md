# Drools 7.74.1 and Apache KIE 10.2.0 re-run on a cloud VM

Re-run of the DMN gap-analysis domain experiment (results/drools/domains, results/tools/kie10) on a quiet
machine, run strictly one JVM at a time. The laptop runs could not measure two things: whether Nursery V1
(full declared values, 6,480 rules) finishes, and clean runtimes.

## Machine

Cloud VM (KVM, Ubuntu 24.04): 4 vCPU Intel Xeon @ 2.10 GHz, 15 GiB RAM, no swap; OpenJDK 21.0.12.1
(Ubuntu build), Maven 3.9.11, Python 3.13.16. Full details are in [MACHINE.md](MACHINE.md). Nothing else ran
during the measurements except a sampler that ran `ps` once a minute and pushed progress during the Nursery V1 runs.

## Method

* Inputs: `python3 run_tool_inputs.py` regenerated the 39 DMN 1.4 files in results/tools/inputs/. The
  regenerated `manifest.json` is byte-identical to the committed one, and every run also asserts the case's
  missing-state count against it.
* Drivers: `results/tools/kie10/pom.xml` + `DroolsCheck.java` (KIE 10.2.0, 59 jars) and
  `tools/drools/pom.xml` + `DroolsCheck.java` (Drools 7.74.1.Final, 39 jars), libraries from
  `mvn dependency:copy-dependencies`, compiled with javac 21. **Both versions ran on the preinstalled
  OpenJDK 21.0.12.1.** Drools 7.74.1 worked on Java 21 for every file, so no older JDK was installed.
  The laptop used Temurin 8 (7.74.1) and Temurin 17 (10.2.0).
* Runner: [run_cloud.py](run_cloud.py), a Linux copy of results/tools/kie10/run_kie10.py. Each file
  gets one JVM: `/usr/bin/time -v timeout -s KILL <cap> java -Xmx<heap> DroolsCheck <file>`. Wall time and
  peak RSS come from GNU time and include JVM start-up. The output is evaluated with
  `latc_check.drools_domains.evaluate` (gap tokens read over the declared domains for V1/V3b, the
  observed domains for V4, and none for V2) and compared field by field with the laptop result for the same tool
  (results/tools/kie10/results.json for 10.2.0, results/drools/domains/results.json for 7.74.1).
* Timing pairs: pension (12 files) and Car (24 files), variants V1, V2, V3b, V4, with -Xmx8g and a 30 min cap,
  first on 10.2.0, then on 7.74.1.
* Nursery finance=convenient: V1 with -Xmx12g and a 2 h cap (10.2.0, then 7.74.1 because 10.2.0 finished),
  then V2 on both. Long runs were started detached (`nohup setsid`). [watch_long.sh](watch_long.sh) sampled
  the JVM RSS every minute (raw/*_nursery_V1.rss.tsv) and pushed PROGRESS.md about every 9 min.
* Raw validator output for every run: raw/<tool>/<file>.txt; GNU time output: raw/<tool>/<file>.time.
  Per-run results: [results.json](results.json). The tables below are generated by [summarize.py](summarize.py).

## Results in brief

* **Laptop and cloud agree on every comparable run**: 37/37 for Drools 7.74.1 and 37/37 for KIE 10.2.0
  (pension, Car and Nursery V2). Outcome, gap count, states covered, extra states, removed-value states,
  skip columns, message types and the first gap messages are all identical, even though the JDK changed
  (8/17 to 21). The domain finding holds: V1/V3b report gaps covering exactly the missing states, V2 skips gap
  analysis, and V4 (inputValues copied from the rules) finds 0 removed-value states. On Car, V4 gives a false
  "no gaps". On pension it reports only the gaps inside the observed product.
* **Nursery V1 finishes on both versions on this machine.** The laptop runs were killed (7.74.1 after about 61 min
  with a 1.2 GB heap; 10.2.0 at its 15 min cap).
  * Drools 7.74.1: 2,076 s (34.6 min), peak RSS 1,303 MB.
  * KIE 10.2.0: 2,401 s (40.0 min), peak RSS 2,265 MB.
  * Both report 720 `DECISION_TABLE_GAP` messages covering all 6,480 missing states with 0 extra states, and
    find all 6,480 removed-value states. The two versions print the same set of 736 messages (720 gap,
    10 contraction, 6 second-normal-form).
  * Both runs used 1 core (about 100% CPU) the whole time. RSS stayed flat (10.2.0 at 2.0-2.2 GB from the first minute;
    7.74.1 rising slowly from 1.1 to 1.3 GB), so memory was not the limit with 12 GB available. Whether the
    laptop's 1.2 GB heap was enough for 7.74.1 is not tested here: 7.74.1 peaked at 1.3 GB RSS, which includes
    non-heap memory.
  * A thread dump of 10.2.0 at 28 min ([raw/kie10_nursery_V1.jstack_28min.txt](raw/kie10_nursery_V1.jstack_28min.txt))
    shows the main thread in `DTAnalysis.computeContractions` (contraction-rule analysis).
    `DMNDTAnalyser.dmnDTAnalysis` calls `findGaps` first, then overlaps, masked/misleading rules,
    normalisation, subsumption, contractions and the normal-form checks. So gap analysis itself had already finished
    by then, and most of the run time is spent after it. The driver prints nothing until `validate()`
    returns, so this run cannot time the gap step alone.
* **Runtime, same machine:** 7.74.1 is slightly faster than 10.2.0 on pension (14.1 s vs 16.8 s for 12 files, mostly
  JVM and library start-up) and on Car (214.8 s vs 229.1 s for 24 files), and takes about 14% less time on Nursery V1 (34.6
  vs 40.0 min). The laptop totals (Car: 785 s and 1,129 s) were 3.7 to 4.9 times higher and reversed nothing
  in the ranking, but they are not comparable to these figures: different machine, different JDKs, and memory contention.
* Nursery V2 (no declared values): "gap analysis skipped" on both, the same as on the laptop. It takes 24 s (7.74.1) and 30 s
  (10.2.0) here vs about 104 s and 102.5 s on the laptop. Its peak RSS (2.1 to 2.7 GB) is higher than the V1 runs'
  because with -Xmx12g the JVM grows the heap freely during parsing. Peak RSS shows how the JVM sized its heap, not how much memory the analysis needs.

## Not run / caveats

* Everything in the task was run, and no run hit its cap.
* No older JDK was needed or installed, so the 7.74.1 numbers are on Java 21, not on Java 8 as on the laptop.
  The outcomes match the Java 8 results exactly.
* The Nursery V1 timings are from one run each, on a shared cloud VM (4 vCPU, no other user load visible).
  Only V1 and V2 of one Nursery case (finance=convenient) were run.
* KIE 10.2.0 Nursery V1 wall time was 40:00.50 (h:mm:ss) by GNU time, with exit status 0 and complete output (736
  messages). The round number is a coincidence: the cap was 7,200 s.
* The thread dump is the only intervention during a timed run. jstack pauses the JVM briefly, which is negligible against a 40 min run.
