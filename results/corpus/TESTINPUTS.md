# Test inputs that no rule mentions

Generated by `run_dmn_testinputs.py` (`latc_check/dmn_testinputs.py`). Question: do the test cases shipped with public DMN models feed a decision table a string value that no rule entry of the column mentions (the value an observed-domain analyser never reports missing)? The corpus and the table and column measures are those of `SUMMARY.md` (`dmn_corpus.py`), which this survey leaves unchanged.

## Formats

* **DMN TCK test cases** (`*-test-NN.xml`, `<testCase>` / `<inputNode>`), parsed, with the model named by `<modelName>` in the same folder. Only the DMN TCK clone holds them on disk.
* **Not parsed**: Drools / KIE `.scesim` scenarios, JSON / YAML fixtures and unit tests written in code. The other 49 sources are blob-less sparse clones with `.dmn` files only, so these files are not on disk; reading them would require downloading. Their number, counted from the local git trees (file names only), is under *Skipped formats*. Unit tests in Java, JavaScript or Scala are skipped in any case: linking a value to a model input would need the host code evaluated.

## Resolution

A test case evaluates its result decisions and every decision they require (transitively), or the output and encapsulated decisions of a tested decision service; when no result node names a decision, every decision of the model counts. A decision table owned by one of them has each input expression (`A` or `A.b.c`) matched to the test case's input nodes, components followed for dotted paths. A table of a business knowledge model is reached when the test invokes the BKM, or an evaluated decision invokes it with parameters bound to plain input names. A *link* is one (test value, table column) pair; a *resolved input value* is an input node that feeds at least one column.

## Checks

For links into a string column whose entries mention at least one string literal (as in `SUMMARY.md`), a string test value is *unmentioned* when no entry of the column mentions it (exact match against the decoded literals; `not(...)` lists and literals inside expressions count as mentions). Whether a rule can still match it: *wildcard* (some entry is `-` or empty), *not* (a `not(...)` entry admits it), *unknown* (an entry is a FEEL expression), *no match* (every entry is a literal list and none admits it: no rule of the table matches, the table returns no result or its default output).

## Caveats

* Only TCK test cases are measured; the TCK exercises engine conformance, so its test values are chosen to hit rules, and its numbers say little about business test suites.
* Resolution is static: input expressions that are FEEL expressions other than a name or a path, tables inside contexts whose variables shadow inputs, BKMs invoked through other BKMs or with computed arguments, and imported models are not followed (counted under *Unresolved*).
* Matching is exact on the decoded string; *near* matches (case or surrounding blanks) are recorded in `testinputs.json` (`near_mention`).
* *No match* is decided on the column alone. A *wildcard* column can still leave the test value without a matching rule when the other columns exclude it; that would need evaluation.
