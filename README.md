# latc_check: independent checks for finite-domain decision-table completion

This is the reproducibility package for *Cardinality Is Not Enough: Re-examining LATC
Completion of Finite-Domain Decision Tables* (C. A. Russell), a re-examination of
Raggio & Russell, "Business Rules (BR); Expert Systems (KBS); LATC Algorithm. A proposal
for functional integration", *International Journal of Scientific & Engineering
Research* 12(1), January 2021. Every number in that paper is regenerated by
`run_report.py`; its Appendix C maps each result to the module and output file that
produces it. The same package supports the companion paper on LLM-assisted rule
acquisition (*A Human-Governed Architecture for LLM-Assisted Business Rule Acquisition and
Finite-Domain Decision-Table Completion*), whose research questions RQ2 and RQ4 are
named below.

This work is dedicated to the memory of Raul A. Raggio, co-author of the LATC algorithm.

It answers two questions that need independent evidence:

* **RQ2, completion correctness.** Does LATC return exactly the set-theoretic
  complement of the expert's initial table T0, or should completion be explicit
  enumeration with LATC's counts kept only as a check?
* **RQ4, operations.** Is a completed table structurally sound (coverage, single-hit,
  conflicts, out-of-range referral)? What do prime-product and SHA-512 keys actually
  guarantee? How do build time, memory and lookup latency scale?

The package uses only the standard library, needs Python ≥ 3.10, and has no dependencies.

```bash
python run_report.py
```

```bash
python -m unittest discover -s tests -t .
```

`run_report.py` prints the report and writes `results/results.json` and
`results/benchmark.csv`, plus `results/dmn_benchmark.csv` and DMN 1.4 XML files in
`results/dmn/`. Options: `--trials N` (default 1000 random tables per
scenario), `--seed S`, `--max-rows R` (benchmark cap, default 300 000), `--dmn-max-space R` (largest space timed
for the DMN baseline), `--skip-bench`.

`--large` adds the large-scale test, which takes several minutes and writes
`results/large.csv`. `--large-only` runs just that test and merges its results into an
existing `results.json`. The size of the test is set with `--large-max-rows` (default
70M), `--large-heavy-max-rows` (default 4.2M), `--large-probes` (default 100 000) and
`--large-t0` (default 1000).
All results except the timings are fully determined by the seed. `results_report.txt`
holds the output of the reference run.

## Source and interpretive choices

**Tables.** The worked example uses the real T0 rows of Table 1a and the published
complementary table, transcribed from the IJSER article and checked cell by cell against
the manuscript submitted to the journal, where the tables are images (status
`CHECKED_AGAINST_IJSER_MANUSCRIPT`). The frequency table (M 4, F 4; D 3, I 5; ≥30 5,
<30 3; ≥65 3, 60–64 4, <60 1) and the deficits (8/8, 9/7, 7/9, 5/4/7) are reproduced
exactly.

The source's formulas are intact as Word equations in the manuscript submitted to IJSER;
plain-text extraction drops them. Every step below is documented in `latc.py`:

* **I-1** Card(Ai) counts the distinct values *that appear in T0*. Declared domains are
  not consulted.
* **I-2** Frequencies count rows, duplicates included. Values are listed in order of
  first appearance, which reproduces the order of the source's frequency table.
* **I-3** Corollary 3 [11b]: missing = ∏ Card(Ai) − q(T0).
* **I-4** Corollary 4 [12]: k(Ax = v) = ∏ Card / Card(Ax) − freq(Ax = v).
* **I-5** The source has no valid-state constraint.

The appendix of the IJSER article specifies Reading B. Reading A is a shortcut the main text's description of Corollary 4 admits, and is kept to show why it
fails:

* **Reading A, deficit block fill.** The shortcut suggested by "columns filled in
  frequency-table order, each column filled with value blocks in sequence". Each column
  is filled independently with k(v) copies of each value. The row-level critique applies
  to this reading.
* **Reading B, odometer assembly.** The IJSER appendix builds the table from the *summed*
  frequencies of T0 ∪ Cp, using a per-column "quantity of repetitions", and then matches
  the T0 rows (footnote 7). The worked example's completed Table 9 shows all 24 rows in
  odometer order, with the T0 rows marked by instance number. Under this reading LATC is
  explicit enumeration plus membership matching. The source gives the repetition count as
  CR_j = Card(C⁰) / ∏_{k=1..j} Card(Ak), which equals r_j = ∏_{k>j} Card(Ak), the block
  length used here.

## Results (reference run, seed 20210101)

**Worked example.** T0 has 8 rows; ∏ Card = 24; missing = 16.

* The **published complementary table equals the exact complement** (16/16).
* **Reading A** gets 13 of the 16 rows wrong. Its output has 11 duplicate rows and 6 rows
  that regenerate T0. No ordering of the value blocks fixes it: the best of all 48
  orderings still misses 10.
* Reading A's marginals equal the deficits, and the source's own "sum of frequencies"
  check passes on T0 ∪ Reading A. **The count checks cannot detect the error.**
* **586** distinct 16-row sets match the deficit table exactly. Only one of them is
  disjoint from T0, and that one is the complement. Marginal counts do not determine the
  missing set.
* **Reading B** is exact.

**Counterexample.** T0 = {(M,D),(F,I)}. Reading A regenerates T0 instead of
{(M,I),(F,D)}. The twin table {(M,I),(F,D)} has the same frequency table and the
opposite complement, so a fill rule that reads only the counts can be right for at most
one of the two.

**Random tables** (1000 per scenario; 2–4 attributes, 2–4 values):

| scenario | reference | Reading A | Reading A, best order | Reading B |
|---|---|---|---|---|
| all values observed, no constraint | 100 % | 26.3 % | 48.3 % | 100 % |
| one declared value unobserved in T0 | 100 % | 0 % | 0 % | 0 % (misses 8.9 rows on average) |
| valid-state constraint | 100 % | 0 % | 0 % | 0 % (6.3 invalid rows on average) |

The figures are exact-equality rates. When a value is unobserved or a constraint
applies, Corollary 3's count is wrong in 100 % of cases. The generalised check in
`valid_space_deficits` (marginals of the declared valid space minus T0) holds in every
scenario.

**Operations.**

* The completed pension table is sound: coverage 1, single-hit, no conflicts. An
  injected conflicting duplicate is detected.
* All 8 out-of-domain probes go to `Out of Range` under all three key back ends.
* Distinct primes give 24 distinct keys (13 bits). The ambiguous assignment (the j-th
  value of every attribute gets the j-th prime) gives only 9 distinct keys for 24 rows.
* With SHA-512 truncated to 8 bits, the verified index is right for 1024/1024 lookups.
  Digest-only lookup is right for 254/1024.
* Prime keys pass 64 bits at 10 attributes × 8 values (73 bits).
* Benchmark: up to 262 144 rows built in 5.5 s with a 114 MiB traced peak.
* Per-lookup medians: canonicalisation ≈ 13 µs (pure Python `json`), SHA-512 ≈ 1.1 µs,
  verified probe ≈ 0.2 µs. Canonicalisation dominates lookup cost.

## Baseline B4: DMN gap and overlap analysis

`dmn.py` follows the geometric reading of Calvanese et al. (BPM 2016; Information Systems
2018). Rules are hyper-rectangles. The analysis sweeps one dimension at a time and keeps
the set of rules active in each slab. An empty slab is a missing-rule region. Two or more
rules active in a last-dimension segment form overlapping pairs. Adjacent gap regions are
then merged.

The implementation works from the published description, not from the authors' tool.
Its interpretive choices, D-1 to D-7, are listed in the module docstring:

* **D-1** Numeric inputs are real intervals with exact open and closed bounds. Integer
  inputs are not special-cased.
* **D-2** An enumerated input's domain is its declared allowed values. Variants that use
  only the values T0 mentions are also reported.
* **D-3** Within a dimension, cells with the same active rules are grouped into one
  segment. Enumerated values are grouped in declared order by default, or as a set
  (list entries) if chosen.
* **D-4** Gap merging is greedy and runs to a fixed point. The result is not guaranteed
  minimal.
* **D-5** The overlap set does not depend on the hit policy:
  * UNIQUE flags every overlapping pair;
  * ANY flags pairs with different outputs;
  * FIRST only reports pairs as masked.
* **D-6** DMN has no valid-state constraint.
* **D-7** Entries are clipped to the declared domains.

Converters go both ways. Exact tuples become point entries, and the declared bins become
intervals. A DMN table becomes exact tuples through the declared bins; entries that only
partly cover a bin are flagged.

Results from the reference run:

| check | DMN analysis | COMPLETE |
|---|---|---|
| (a) T0 = Table 1a as 8 rules | 7 gap regions (10 before merging), expanding to 16 tuples; 0 overlaps | 16 rows; same set ✔ |
| (b) completed rule written compactly | 8 UNIQUE rules with 25 non-`-` cells; 0 gaps, 0 overlaps | 24 rows with 96 cells; coverage 1, single-hit; same outcomes ✔ |
| (b) seeded fault: drop one rule | 1 region / 1 tuple | 1 uncovered tuple ✔ |
| (b) seeded fault: widen one rule's Age range | 3 overlapping pairs (3 UNIQUE violations) | 4 multi-hit, 4 conflicting tuples ✔ |
| (c) raw Table 1 (≥65, ≥60, <60, <65) | 0 overlapping pairs under every hit policy; 4 gap regions / 12 tuples | 12 rows on the discretised raw table ✔ |
| (d) counterexample and its twin | exact for both | exact for both |
| (d) random, all values observed | 100 % exact | 100 % |
| (d) random, unobserved declared value | 100 % with declared values; 0 % with values taken from T0 | 100 % |
| (d) random, constraint | 0 % natively (6.3 impossible states per table reported as gaps); 100 % after filtering by the constraint outside DMN | 100 % |

Notes on these results:

* **The two methods agree as sets.** Wherever the input domains are declared, the
  expanded DMN gaps are exactly COMPLETE's rows.
* **What DMN adds:**
  * a compact presentation: about half as many regions as missing points or fewer on random
    tables, 7 against 16 on the pension example;
  * native interval semantics.
* **What COMPLETE adds:**
  * a valid-state constraint;
  * one reviewable row per case, each with its own outcome cell for the experts.

  A DMN gap region still has to be split wherever the experts assign different outcomes
  within it.
* **Raw Table 1 has no Unique violations.** The overlapping Age labels never meet in rows
  that agree on the other inputs. The sweep's elementary Age cells (60 and 65 as
  boundaries) are the normalised bins.
* **The normalisation to Table 1a was not semantics-preserving.** It narrowed rows 3, 4,
  7 and 8 from two Age bins to one, and it changed the outcomes of rows 6 and 8. As a
  result the raw rules cover 12 tuples and Table 1a covers 8.
* **LATC on the raw labels** treats them as 4 opaque Age values: ∏ Card = 32 and
  "missing" = 24.
* **Timing** uses T0 = a random half of the space, which is the worst case for region
  merging. Analysis grows with the number of gap regions. COMPLETE is roughly 10–50× faster on
  point tables up to 262 144 cells (0.21 s against 9.4 s). The DMN sweep, however, also
  handles interval entries without expanding them.
* **The XML** in `results/dmn/` is well-formed and parses against the DMN 1.4 namespace
  in the tests. It has **not** been opened in an external DMN tool. The paper session
  should also check the D-1 to D-7 choices against the Calvanese et al. papers before
  citing them as "their algorithm".

## Large-scale test (`--large`)

The test builds complete tables over declared domains in seven shapes:

* 1M rows: 10 attributes × 4 values, and 20 × 2;
* 4M rows: 11 × 4;
* 16.8M rows: 12 × 4, plus a deep, narrow shape (24 × 2) and a wide, shallow one (4 × 64);
* 67M rows: 13 × 4.

T0 is 1000 random rows. Outcomes for the completed rows are synthetic, since only sizes
and lookups are measured.

**Machine.** Intel Core i7-1165G7 (4 cores, 8 threads), 15.7 GiB RAM with only 1–1.7 GiB
free during the run, Windows 11, CPython 3.15.0. Every structure except the rank index is
built only if its projected size fits in 60 % of the free memory at run time. Otherwise
the projection is reported in its place. Projections come from traced bytes per row over
the first 100k rows.

| shape | rows | COMPLETE stream | rank index build | rank size / load | dict (canonical bytes) | SHA-512, verified | prime keys | prime-key bits |
|---|---|---|---|---|---|---|---|---|
| 10×4 | 1.05M | 0.2 s | 0.2 s | 1 MiB / 0.06 s | 1.6 s, 186 MiB on disk | 4.4 s, 255 MiB | 4.9 s, 12 MiB | 60 |
| 20×2 | 1.05M | 0.3 s | 0.2 s | 1 MiB | 2.4 s, 369 MiB | 4.5 s, 438 MiB | 5.0 s, 19 MiB | 115 |
| 11×4 | 4.2M | 0.7 s | 0.8 s | 4 MiB | 11.1 s, 816 MiB | skipped (1.7 GiB) | 16 s, 52 MiB | 67 |
| 12×4 | 16.8M | 3.8 s | 3.6 s | 16 MiB / 0.07 s | skipped (4.7 GiB) | skipped (7.2 GiB) | skipped (1.8 GiB) | 75 |
| 24×2 deep | 16.8M | 4.0 s | 3.4 s | 16 MiB | skipped (8.1 GiB) | skipped (10.6 GiB) | skipped (1.9 GiB) | 146 |
| 4×64 wide | 16.8M | 1.8 s | 12.7 s* | 16 MiB | skipped (2.7 GiB) | skipped (5.0 GiB) | skipped (1.7 GiB) | 39 |
| 13×4 | 67.1M | 12.0 s | 20.3 s | 64 MiB / 0.16 s | skipped (20 GiB) | skipped (30 GiB) | skipped (7.1 GiB) | 83 |

How to read the table:

* The dict, SHA-512 and prime columns give build time and pickled size, or the projected
  in-memory size when the build was skipped.
* \* The 4×64 rank build is the same loop as the others. Its 12.7 s most likely reflects
  memory pressure from other programs on the machine during the run.
* Streaming COMPLETE uses about 1 KiB of traced memory at every size, plus 157 KiB for
  the T0 key set.
* Streaming the same complement as ranks (integers instead of tuples) takes 0.8–3.5 s
  instead of 1.8–12 s.
* Prime keys pass 64 bits from 11×4 upward, and at 1M rows when there are 20 binary
  attributes.
* The rank index matched the dict on all 100 000 probes wherever the dict was built. At
  larger sizes it was checked against enumeration order on the first and last 100k rows.

**Lookup latency** (median / p99, µs, 100 000 random probes, 12×4 shape):

| step | median / p99 |
|---|---|
| generic canonicalisation | 38 / 124 |
| canonicalisation with cached fragments | 1.0 / 2.3 |
| SHA-512 of the canonical bytes | 1.5 / 3.5 |
| prime key | 2.4 / 9.3 |
| rank computation | 1.4 / 3.0 |
| array read | 0.2 / 0.5 |
| **rank lookup, end to end** | **1.5 / 3.5** |

At 1M rows (10×4) the end-to-end figures are: dict 2.1, SHA-512 verified 4.8, prime 3.3
and rank 2.2 µs. Windows `perf_counter_ns` ticks in 100 ns steps, so sub-µs values are
coarse.

**DMN.** The sweep analysis of the 1000 sparse T0 rules against the full space finishes
at every size: 0.25–2.9 s, 4.5k–11.8k gap regions. The dense case (all rows but T0 as
point rules) needs about 3.7–7 KB per rule in this implementation, roughly 4–7 GiB at
1M rules. It was skipped on this machine. The B4.5 grid shows it finishing at 262 144
cells in 9.4 s. Above roughly 10⁶ point rules it is not practical in pure Python.

**Review cost** at an illustrative 30 s per row (1 person-year = 1760 h, an assumption):

| rows to review | hours | person-years |
|---|---|---|
| 1.05M | 8 730 | 5.0 |
| 4.2M | 34 944 | 19.9 |
| 16.8M | 139 802 | 79.4 |
| 67.1M | 559 232 | 317.7 |

Reviewing one outcome per DMN gap region instead would take 38–98 h. That is a lower
bound, valid only if the experts accept one outcome for regions that span up to
millions of cases, which is a generalisation decision rather than a computation.

**Where the cost comes from:**

* **Inherent to the problem.** Rows grow as Π|Dᵢ|. Any complete table needs at least
  one outcome per row, which the rank index stores in 1 byte (16 MiB at 16.8M rows,
  64 MiB at 67M). Review time is linear in rows.
* **Pure-Python overhead, avoidable:**
  * Generic canonicalisation costs about 40 µs, against about 1 µs with cached
    fragments.
  * Building one tuple per row is about 3× the cost of streaming ranks.
  * The dict, SHA-512 and prime structures cost 100–500 bytes per row in CPython object
    overhead, against 1 byte for the array.
  * The DMN sweep's per-cell `frozenset`s set its memory limit.
* **What numpy would change** (not added; stdlib only). It would vectorise rank
  computation for batches of probes (`ravel_multi_index`) and the code-array fill,
  likely by 10–100×. PyPy would speed up the per-row loops. Neither changes the row
  count, the 1 byte-per-row floor or the review cost.

## What the evidence supports, and what it does not

* LATC under Reading A **does not** return the complement. Under Reading B it does, but
  only when every declared value appears in T0 and there is no constraint. In that
  setting LATC *is* enumeration. The paper should specify completion as explicit
  enumeration of the declared valid space minus T0, and keep the deficits, generalised to
  the valid space, as a cross-check. A check that passes is necessary but not sufficient.
* "Provably consistent" does not follow from unique keys. Unique keys establish row
  identity (single-hit). Outcome consistency is an expert judgement on the assigned
  outcomes; `test_unique_keys_do_not_imply_consistent_outcomes` illustrates this.
* SHA-512 is not injective. A digest index is safe only if it verifies the canonical
  tuple on every hit.
* Prime products are guaranteed injective with a one-to-one (attribute, value) → prime
  assignment and exactly one value per attribute. Reusing a prime within an attribute
  always collides; reusing one across attributes may or may not, so it must be checked.
* Canonical bytes follow RFC 8785 for strings, safe integers, booleans and null only.
  Floats are rejected, and values are not Unicode-normalised, so domains should be
  declared in NFC.
* The operating ranges used for the out-of-range tests (Age 18–120, contribution years
  0–60) are assumptions; the source does not state them.

## Source discrepancies noted while transcribing

* "q(Ci0) = 18" should be 8.
* The Contribution-years domain is printed as {≥30; >30}; it should be {≥30; <30}.
* The Contents table prints "Sex 6" as the missing-instances total; it should be 16.
* Table 1 → Table 1a changes two outcomes: row 6 YES → Rv and row 8 Rv → YES. The swap
  is the same in the Word file submitted to IJSER. Table 1a agrees with the experts'
  outcomes for the complementary rows (age-eligible, fewer than 30 contribution years:
  D → YES, I → Rv), so it is taken as the intended version.
* The Age value order in the completed Table 9 (<60, 60–64, ≥65) is the reverse of the
  frequency table's order.
* In Table 9, the block of rows 10–12 (M, I, <30) lists Age as ≥65, <60, 60–64, unlike
  every other block. All 24 states still appear once.
* Table 9 prints row 6's final result as "SI" (Spanish); it is read as YES.
